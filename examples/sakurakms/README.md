# SAKURA Cloud KMS example

An example `transhim.Backend` for [SAKURA Cloud KMS](https://manual.sakura.ad.jp/cloud/appliance/kms/index.html) (package `sakurakms`), and an example server for Ceph RGW built on it (`cmd/transhim-sakurakms`). It is a Go module of its own, so that the SAKURA Cloud SDK is not a dependency of transhim. Copy and adapt it.

## The backend

```go
var sa saclient.Client
apiClient, err := kms.NewClient(&sa) // github.com/sacloud/sacloud-sdk-go/api/kms
backend := sakurakms.New(kms.NewKeyOp(apiClient), sakurakms.WithKeys(map[string]string{
	"my-key": "123456789012", // key name -> resource ID of the KMS key
}))
```

- `Encrypt` and `Decrypt` call the KMS encrypt and decrypt APIs, with AES-256-GCM.
- A key name is resolved to the resource ID of a KMS key by `WithKeys` or `WithKeyID`. Names that are not listed are answered as not found. Without either option the key name itself is the resource ID.
- KMS keys are not created or deleted by the backend. For per-bucket keys (SSE-S3), it serves as the root of a `hierarchical.Backend`.
- KMS has no "generate data key" call, so data keys are generated by transhim and wrapped with `Encrypt`.
- Plaintexts are limited to 1024 bytes (`sakurakms.MaxPlaintextSize`), because KMS limits the size of what it decrypts. Data keys are 64 bytes at most.

### How the AAD is bound

KMS has no parameter for additional authenticated data. The backend encrypts `0x01 || sha256(AAD) || plaintext` and, after decrypting, compares the hash with the one of the request's AAD before it returns anything. The KMS ciphertext is authenticated, so the hash in it cannot be exchanged. A ciphertext made for one mount, key name, and context therefore does not decrypt for another.

Bound into every ciphertext, and therefore not to be changed later:

- That layout.
- The KMS key a key name resolves to. `Decrypt` uses that key, so a ciphertext of any other key fails. Rotating a key in KMS keeps its resource ID and is not affected.

### Errors

The KMS API does not define its error responses, so the backend goes by the HTTP status: `404` is a missing key; `400` is a ciphertext that does not decrypt, or a key that is not active; `401` and `403` are answered with `403`; `429`, `5xx`, and network failures with `503`.

### Speed

A KMS call typically takes seconds, and the SDK client limits itself to 5 requests per second and retries failed calls with a backoff (`SAKURA_RATE_LIMIT`, `SAKURA_RETRY_MAX`, `SAKURA_RETRY_WAIT_MIN`, `SAKURA_RETRY_WAIT_MAX`). Ceph RGW waits as long as it takes. What keeps this bearable:

| request | KMS calls |
|---|---|
| SSE-S3, first encrypted write to a bucket | 1, to wrap the bucket's key |
| SSE-S3, every other write and read | 0 while the bucket's key is in memory (`-key-cache-ttl`), else 1 to unwrap it |
| SSE-KMS, write | 1 per object |
| SSE-KMS, read | 0 while the object's data key is in the decrypt cache (`-decrypt-cache-ttl`), else 1 |

Requests that need the same KMS call at the same time share it.

## The server

```console
$ export SAKURA_ACCESS_TOKEN=... SAKURA_ACCESS_TOKEN_SECRET=...
$ go run ./cmd/transhim-sakurakms -listen :8200 -token-file token \
    -tls-cert cert.pem -tls-key key.pem \
    -key my-key=123456789012 -root-key 123456789013
```

| mount | mount ID | used for | key |
|---|---|---|---|
| `/v1/transit-kms` | `rgw-kms` | SSE-KMS | the KMS key given for the S3 request's key ID with `-key NAME=ID` (repeatable); other key IDs are refused |
| `/v1/transit-sse-s3` | `rgw-sse-s3` | SSE-S3 | one intermediate key per bucket, wrapped by the KMS key `-root-key` |

The matching RGW configuration is in [docs/rgw.md](../../docs/rgw.md).

**The per-bucket keys are kept in memory** (`keystore/memstore`). When the process ends, every SSE-S3 object becomes unreadable. Before storing anything you need, replace it with a durable `hierarchical.KeyStore`; [examples/sqlkeystore](../sqlkeystore) is one on PostgreSQL or SQLite.

## Tests

```console
$ go test ./...
```

The tests run against [sakumock](https://github.com/sacloud/sakumock)'s KMS, started in-process. They need no account and no setup.

To try the server without an account, run sakumock next to it:

```console
$ sakumock kms --key '100000000001=dev-a;100000000002=dev-root' --latency 2s &
$ export SAKURA_ENDPOINTS_KMS=http://127.0.0.1:18081 SAKURA_ACCESS_TOKEN=dummy SAKURA_ACCESS_TOKEN_SECRET=dummy
$ go run ./cmd/transhim-sakurakms -listen 127.0.0.1:8201 -token-file token -insecure-http \
    -key testkey-1=100000000001 -root-key 100000000002
```
